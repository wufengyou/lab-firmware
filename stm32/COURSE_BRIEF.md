# 任務書：把 `stm32/` 教材化

> 給接手教材化的人（目前指派：Codex app）。
> **這份是任務書，不是教材本身**，也不是真相來源 —— 事實一律以 `README.md` 為準。

## 一句話任務

把 `stm32/` 這次「自製 SWD debugger 上機」的過程，改寫成一份**可以教初學者、
也能供工程人員回查證據**的實作教材，房規對齊 `ros_course/CHASSIS_RECONSTRUCTION_LAB.md`。

## 交付物與邊界（先讀這段）

| 項目 | 規定 |
|---|---|
| 新檔位置 | `stm32/COURSE.md`（單檔起步；要拆章再議） |
| **不要改的檔案** | `README.md`、`HANDOVER.md`、`common/*.h`、`cpu_ctrl/`、`swd_probe/`、`Makefile`、`serial.ps1` |
| 發現既有檔有錯 | **回報，不要順手改。** 教材與韌體的修改必須分開評估 |
| commit | 教材自成 commit，不要混進韌體或文件修正 |
| 事實出處 | **`README.md` 是唯一真相來源**。教材**引用**它，不複製數字 |

最後一條是硬性要求：腳位、電壓、`DHCSR` 位元值如果在兩個檔案裡各寫一份，
遲早會分岔，而分岔的文件比沒有文件更糟。需要具體數字時，寫「見 `README.md`
〈四支腳的指紋〉」，或明確標注「以下數值同步自 README，修改時兩邊都要動」。

## 主線：這份教材在教什麼

**不是 SWD 協定教學。** 協定細節網路上到處都有，而且 `common/swd.h` 的協定碼是從
`nano130/` 一字不改搬過來的，不是這次的產出。

這個 repo 的稀缺價值是**推導過程**：卡住 → 換方法 → 驗證 → 發現原本的假設是錯的。
教材如果寫成「第一步接線、第二步燒錄、第三步看結果」，最值錢的部分就沒了。

### 三段教學高價值素材（建議當骨幹）

每一段的共同點是：**結論可以遷移到別的題目**，不只適用這兩片板子。

| 段落 | 在 README 的哪裡 | 可遷移的道理 |
|---|---|---|
| CN3 四支腳的指紋電壓 | 〈最可靠的辨識法〉 | 辨識未知線路，要找「一次標定全部」的量法，不要用「試一次得一個 bit」的試錯法 |
| `C_MASKINTS` 必須單獨寫一次 | 同名小節 | 「編得過」不等於「對」；該驗的是硬體**讀回來**的位元，不是程式**寫進去**的值 |
| Makefile 沒追蹤標頭相依 | 〈指令〉與 Makefile 註解 | 建置系統會**偽造實驗結果** —— 你以為在驗新程式碼，其實跑的是舊的 |

### 一個現成的教學伏筆（建議用）

`C_MASKINTS` 那段有個免費的互動點：**halt 落點的分佈**。

- 修好之前，每次按 `h` 都落在 `0x080026F0`～`0x08002730` 那一小段裡打轉
- 修好之後，散在 `0x08000246` / `0x0800539C` / `0x080026F4`，`SP` 也跟著變

教材可以**先把「打轉」那段輸出丟給讀者、問他覺得正不正常**，再揭曉。這樣問是誠實的
—— 當下也沒人起疑，是把它當成迴圈放過了。**請照實寫成「當時沒發現」，不要寫成
「我們敏銳地注意到」。**

## 房規（對齊 `ros_course/` 既有教材）

1. **開頭放「先看結論，也先看證據等級」表** —— 每一條結論都要標證據等級
   （實測／推論／手冊依據／尚未驗證）。
2. **「生活比喻」+「工程真話」雙欄**，比喻之後一定要接真話，不能只留比喻。
3. **不把「編譯通過」當成驗收。** 這是 `ros_course/` 反覆強調的一條，這裡同樣適用
   —— 而且這次的 `C_MASKINTS` bug 正好是它最好的例證：編得過、看起來也正常、但是錯的。
4. 量測值與推論分開標示。

## 錯誤的推導要留著，這是硬性要求

這個專案的一貫規定：**錯誤的假設要留下並標記為錯，不要刪掉。**

教材化是最容易違反這條的場景 —— 「整理成教材」的本能就是把彎路刪掉、留下乾淨敘事。
但這個 repo 是實驗筆記本，**彎路是教材的素材，不是雜訊**。

至少這三個已標記為錯的推導要進教材，不要洗掉：

- 「接對的話 SWDIO 會是 3.3V」 —— 錯的，會讓人把好的接法誤判成壞的
- 「硬體是 NUCLEO-F446RE ×2」 —— 錯的，實際是 F446RE + L476G-DISCO
- 把線接到 CN4，以及接到 CN3 的 ST-LINK 側 —— 兩個都踩過

## 事實查核：別把推論寫成斷言

`README.md` 已經用 ✅／「推論」標記過，但重寫時最容易在這裡走樣。特別注意這幾個
**是判讀、不是直接量到的**：

- 「~1V 是浮接」 —— 推論（高阻抗腳被電表輸入阻抗拉到電源一半），不是量到 1V 這個電位
- `FLASH` 高 16 bit 是 rev_id —— 手冊依據，實測值可能不同
- CN3 的 pin 編號方向 —— README 已說明「數錯方向不影響結論」，理由要一起帶過去，
  不能只抄結論

## 讀者沒有這兩片板子怎麼辦

**這是教材化必須回答、而目前文件沒處理的問題。** 建議分層，否則讀者會卡在第一頁：

| 層 | 內容 | 需要硬體嗎 |
|---|---|---|
| A | `DHCSR` 位元、ARMv7-M B1.5.15 那條規則、為什麼 `DPIDR`/`CPUID` 證明不了東西 | 不用 |
| B | 讀懂實測輸出、自己判斷哪一行才是證據 | 不用（用文件裡的實測輸出當題目） |
| C | 指紋量測、接線、step 實測 | 要板子 + 三用電表 |

A/B 兩層要能獨立成立。**C 層不要寫成「選讀」草草帶過** —— 它是這份教材唯一無法被
網路文章取代的部分。
